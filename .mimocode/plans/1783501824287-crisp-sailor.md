# Web App Structure Analysis — MARKHINS HUB Attendance System

## Overview

This is a **full-stack attendance management system** for a school, branded as "MARKHINS HUB". It consists of three tightly-coupled services running together in a single Docker container: a **Next.js frontend**, an **Express.js REST API backend**, and a **Telegram bot**, all backed by a shared **SQLite database** and a **Python business logic layer**.

## 3. Service Architecture

### 3a. Express Backend (`backend/server.js`)

**Port:** 8080 (Railway exposes this)

**Key Responsibilities:**
- JWT authentication with single-active-session enforcement
- REST API for all CRUD operations
- Spawns `attendance.py` as a child process for each request (stdin JSON → stdout JSON bridge)
- Activity tracking / audit logging (in-memory ring buffer)
- Teacher photo management (file-based)
- CORS for cross-origin frontend access

**Authentication Flow:**
1. Login → validates against DB (via Python) or hardcoded admin credentials
2. Returns JWT token (7-day expiry)
3. Every protected route: `authenticateToken` middleware verifies JWT + session
4. Admin/Majlis roles have special bypass for session checks

**User Roles:**
- `admin` — Full system access (env-based credentials)
- `Majlis` — Reports-only access (hardcoded credentials: majlis/admin)
- `Principal` — Full health management + cross-class access
- `Vice Principal` — Similar to Principal
- `Urdu Principal` — Scoped to Urdu classes only (hardcoded: MAHROOF QADIRI)
- `Class Teacher` — Health management for assigned class only
- `Subject Teacher` — Basic attendance marking only

**Python Bridge (`callPython`):**
- Spawns `python attendance.py` per request
- Passes JSON payload via stdin
- Reads JSON response from stdout (regex-parses last JSON object)
- 10-second timeout protection
- ~40+ distinct `action` types

**API Endpoints (grouped):**
- **Auth:** `/login`, `/validate-token`
- **Core Data:** `/classes`, `/subjects`, `/students`, `/timetable/:class`
- **Attendance:** `/mark-attendance`, `/attendance/last`, `/attendance/edit-last`, `/attendance/marked-periods`, `/attendance/extra`
- **Period Resolution:** `/resolve-period`, `/full-timetable/:weekday`
- **Health:** `/health/sick-list`, `/health/leave-list`, `/health/:type`
- **Reports:** `/daily-report`, `/weekly-report`, `/batch-report/:classId`, `/class-averages`, `/period-summary`, `/student-history/:rollNo`, `/extra-classes-report`, `/teacher-register-report`, `/absentees-report`
- **Namaz/Events:** `/namaz-analytics`, `/event-attendance`, `/api/namaz-session`
- **Syllabus:** `/api/syllabus`, `/api/syllabus/config`, `/api/syllabus/progress`
- **Profile:** `/profile/me`, `/profile/teaching-stats`, `/profile/update-credentials`
- **Announcements:** `/announcements/*`
- **Admin:** `/admin/teachers`, `/admin/timetable`, `/admin/announcements`, `/admin/upload-db`, `/admin/download-db`, `/admin/activity-log`, `/admin/revoke-session`, `/admin/update-password`, `/admin/reset-namaz-data`
- **Substitute:** `/api/substitute/*`
- **System:** `/health`, `/api/track-event`

**Port:** 3000 (dev) / proxied in production

**Pages:**

| Route | Component | Purpose |
|-------|-----------|---------|
| `/` | `page.js` | Main dashboard (~1300+ lines) — tabs: Attendance, Timetable, Reports |
| `/login` | `login/page.js` | Credential login form |
| `/login-transition` | `login-transition/page.js` | Branded post-login animation |
| `/attendance` | `attendance/page.js` | Standalone attendance marking (386 lines) |
| `/health` | `health/page.js` | Sick/leave management (603 lines) |
| `/extra` | `extra/page.js` | Extra class attendance (259 lines) |
| `/teachers` | `teachers/page.js` | Teacher directory listing (134 lines) |
| `/profile` | `profile/page.js` | Profile view + credential update (266 lines) |
| `/settings` | `settings/page.js` | Admin panel — teachers, timetable, announcements, DB, activity (974 lines) |

**Dashboard Tabs (in `page.js`):**
1. **Attendance** — Class/period selector, marked periods, last attendance card, syllabus quick-view
2. **Timetable** — Full weekly timetable with day selector, zoom controls
3. **Reports** — Sub-types: Overview, Analysis, Syllabus, Namaz, Events, Extra Classes, Register, Substitute

**State Management:** React Context only (AuthContext, LoadingContext). No Redux/Zustand.

**API Proxy:** `/api/proxy/[...path]` — Next.js API route that forwards requests to the Railway backend (handles teacher photos).

### 3c. Telegram Bot (`index.cjs`)

**~3000+ lines.** Uses `node-telegram-bot-api` with polling.

**Features:**
- Interactive inline-keyboard menus (Mark Attendance, Health, Reports, Extra Class, Teacher Options)
- Multi-step attendance flow: Period → Class → Student Toggle → Confirm
- Attendance editing (inline "Edit Attendance" button)
- Admin panel (debug mode, DB backup, error logs, maintenance mode)
- Teacher management (add/edit/remove via text commands)
- Daily DB backup to admin chat
- Access control via teacher database lookup

### 3d. Python Business Logic (`attendance.py`)

**~4000+ lines.** The core brain of the system.

**Communication:** stdin JSON → stdout JSON (spawned as CLI per request)

**Key Functions:**
- Database migrations (auto-runs on startup)
- Teacher login/session management
- Attendance CRUD (mark, edit, view)
- Student health tracking (sick/leave/cure/return)
- Timetable management
- Report generation (daily, weekly, batch, student history, class averages)
- Syllabus tracking
- Namaz attendance tracking (external API integration)
- Event attendance
- Substitute teacher management
- Teacher register/digital register generation

**Database Tables (20+):**
- `students`, `teachers`, `attendance`, `period_attendance`
- `timetable`, `teacher_subjects`, `extra_classes`
- `substitute_log`, `manual_substitute_assignments`
- `system_settings`, `admins`
- `teacher_announcements`, `announcement_broadcasts`
- `namaz_sessions`, `namaz_attendance`, `namaz_api_events`
- `syllabus_configs`, `syllabus_monthly_targets`, `syllabus_progress`

### 3e. DB Manager Bot (`db_manager_bot.py`)

**160 lines.** Standalone Telegram bot for database operations:
- `/download_db` — Send current DB file
- `/backup_db` — Create timestamped backup
- `/restore_backup` — Restore from `.backup` file
- Upload `.db` file to replace database

## 4. Data Flow

1. **Frontend** makes HTTP requests to `NEXT_PUBLIC_API_URL` (or proxy)
2. **Express backend** receives request → verifies JWT → calls `callPython(action, data)`
3. **Python script** spawns, reads JSON from stdin, processes, writes JSON to stdout
4. **Express** parses JSON response, returns to frontend
5. All data persists in **SQLite** (`attendance.db`)

**Telegram path is parallel:**
1. Telegram Bot receives message → calls `callPython()` directly
2. Same Python script, same database

---

## 5. Deployment

- **Docker:** Single container runs all 3 Node.js services + Python via `npm start`
- **Platform:** Railway (backend API URL: `markhins-webapp.up.railway.app`)
- **Environment variables:** JWT_SECRET, TELEGRAM_BOT_TOKEN, ADMIN_CHAT_ID, WEB_ADMIN_USERNAME/PASSWORD, ATTENDANCE_DB_PATH, NAMAZ_API_KEY
- **Database:** Persistent volume at `/data/web_attendance.db` (or local `attendance.db`)

---

## 6. Key Observations

1. **Monolithic dashboard:** The main `page.js` is 1300+ lines with 50+ useState hooks — a single-page app masquerading as a Next.js route
2. **No component decomposition:** Most pages are single-file components with inline rendering logic
3. **Python as database layer:** Every DB operation spawns a new Python process (performance concern)
4. **Hardcoded values:** Admin usernames, Telegram IDs, and role checks scattered throughout
5. **No tests:** No test files found in the codebase
6. **No TypeScript:** Entire frontend is plain JavaScript
7. **PWA-ready:** Has manifest.js, icons, and offline-capable structure
8. **Sound feedback:** Rich audio UX (login, attendance success/error, upload sounds)
9. **Indian school context:** IST timezone handling, Urdu class support, Namaz tracking
